# Cleaning Autopilot — требования к MVP1

## 1. Статус документа

Этот документ задаёт продуктовые и технические границы MVP1. Он является исходным контрактом для проектирования, реализации и приёмки первой версии, а не журналом текущего состояния проекта.

Текущее состояние реализации, принятые архитектурные решения и следующий шаг фиксируются отдельно в корневом `PROJECT_CONTEXT.md`.

Если этот документ расходится с фактическим кодом или `PROJECT_CONTEXT.md`, расхождение нельзя разрешать молча: его нужно явно описать и согласовать с владельцем проекта.

## 2. Цель MVP1

Собрать рабочий прототип автоматизации небольшого сервиса уборки в Белграде.

Основной сценарий:

```text
клиент пишет Telegram-боту
→ AI-агент собирает недостающие данные
→ backend детерминированно рассчитывает стоимость
→ клиент получает quote
→ агент проверяет доступность двух команд в Google Calendar
→ клиент выбирает свободный слот
→ создаётся бронирование
→ Trello и Google Calendar получают актуальное состояние
```

Если запрос выходит за стандартные правила или агент не уверен в scope, он не придумывает цену или решение, а сохраняет собранные данные и помечает заявку флагом `Human Needed`.

MVP1 должен показать законченный путь `Lead → Booking` при минимальной архитектурной сложности и разумном расходе токенов.

## 3. Границы MVP1

### Входит в MVP1

- Telegram-бот как клиентский интерфейс;
- один AI-агент для полного пути от первого сообщения до бронирования;
- OpenAI Responses API и Conversations API;
- детерминированный расчёт цены на backend;
- расписание двух уборочных команд в Google Calendar;
- Trello как операционная CRM;
- Composio MCP как integration layer для Trello и Google Calendar;
- Demo Console для демонстрации и настройки;
- один заранее созданный Admin через Supabase Auth;
- хранение лидов, диалогов, конфигурации и событий в Supabase PostgreSQL;
- full-stack приложение на Next.js и размещение на Railway;
- ручная передача нестандартных случаев человеку.

### Не входит в MVP1

- Gmail и email-уведомления;
- повторяющиеся или регулярные по расписанию уборки, подписки и автоматический повтор бронирований; при этом один Telegram-клиент может вручную начать новую независимую разовую заявку для другого адреса;
- отдельный этап или раздел `Next Week`;
- multi-agent architecture;
- новая CRM вместо Trello;
- регистрация, приглашения, восстановление пароля и управление несколькими ролями;
- автоматизация фактического выполнения уборки;
- автоматический перевод заказа в `Done`;
- сложная автоматическая логика определения `Lost`;
- dashboard builder;
- показ API keys, OAuth credentials или access tokens во frontend;
- отдельный backend-сервис без доказанной необходимости.

Каждое расширение этих границ требует отдельного согласования.

## Порядок реализации и поставки MVP1

MVP1 реализуется последовательными законченными этапами. Каждый этап должен давать отдельный проверяемый результат и не должен заранее затягивать функциональность следующего этапа.

### Этап 1. Bootstrap инфраструктуры

- инициализировать Git в папке проекта;
- создать минимальное приложение на согласованном стеке;
- подключить базовую конфигурацию Supabase;
- определить безопасную работу с environment variables без сохранения секретов в Git;
- настроить обязательные локальные проверки и основу CI.

Публичный GitHub-репозиторий, первый Pull Request и Railway preview откладываются до готовности первого содержательного vertical slice Этапа 2. Это сокращает инфраструктурную работу вокруг страницы-заглушки и позволяет проверить preview на реальном `Telegram → Quote` flow. Когда публичный репозиторий будет создан, секреты, реальные credentials, персональные данные и demo-пароли нельзя добавлять в Git даже временно.

Этап завершён, когда приложение запускается локально, базовая миграция применяется в безопасной среде, frozen install и проверки проходят. Создание GitHub-репозитория, Railway resources и первого deploy выполняется только после явного подтверждения владельца проекта и не является блокером локальной приёмки Этапа 1.

### Этап 2. Первый тестируемый vertical slice: Telegram → Quote

Первый функциональный результат должен доводить реального тестового клиента до рассчитанной цены без Calendar, Trello и Demo Console.

В этот этап входят:

- Telegram webhook и ответы бота;
- один AI-диалог с сохранением OpenAI conversation mapping;
- создание lead и сохранение собранных данных в Supabase;
- извлечение уже сообщённых параметров и вопросы только о недостающих данных;
- детерминированная backend-функция pricing;
- сообщение клиенту рассчитанного quote;
- сохранение quote и значимых событий в БД;
- безопасная остановка без цены для запроса вне автоматического scope.

Перед окончательной приёмкой Этапа 2 обязательна review-доработка надёжности:

- повтор update со статусом `processed` возвращается как duplicate без side effects;
- update со статусом `failed` можно безопасно заново захватить и обработать, а stale `received` не остаётся заблокированным навсегда;
- разные update одного Telegram chat обрабатываются последовательно и не могут одновременно изменять один lead или одну OpenAI Conversation;
- `Human Needed` остаётся независимым flag и не меняет lifecycle status;
- изменение данных заявки инвалидирует quote только тогда, когда изменились влияющие на цену поля; валидность quote и lifecycle не смешиваются;
- эти сценарии покрыты unit/contract tests, включая failed retry и два конкурентных update одного chat.

Этап завершён, когда основной сценарий можно пройти end-to-end через Telegram, данные и conversation сохраняются в базе, повторная доставка webhook не создаёт дубль, failed update восстанавливается без потери сообщения, сообщения одного chat сериализованы, а pricing и lifecycle rules покрыты unit tests.

### Этап 3. Booking

Этап начинается с отдельного подэтапа `3A — Agents SDK migration`. Существующий `AgentGateway` сохраняется как граница приложения, но его самописный OpenAI loop заменяется одним агентом на OpenAI Agents SDK. Агент продолжает использовать существующий OpenAI `conversationId`; текущие strict tools, лимит шагов и поведение Этапа 2 сначала переносятся без добавления Calendar side effects и проходят parity tests. Multi-agent, handoffs и отдельные specialist agents в MVP1 не добавляются.

После принятия parity-проверки подэтап `3B — Calendar reservation` подключает Google Calendar: читать доступность двух команд, предлагать реальные слоты и создавать одно событие после однозначного выбора клиента.

До появления Trello-синхронизации Calendar event означает подтверждённую резервацию слота, но не финальный lifecycle `Booked`: lead остаётся `Qualified` с сохранёнными `calendar_event_id`, командой, интервалом и состоянием pending Trello sync. Клиенту можно сообщить, что слот зарезервирован и финальное подтверждение ожидается, но нельзя сообщать завершённый booking.

Этап завершён, когда `Telegram → Quote → Slot selection → Calendar event → persisted reservation` проверен end-to-end, включая ошибку и повторную обработку без дублирования события. Финальный переход в `Booked` и окончательное клиентское confirmation относятся к Этапу 4.

### Этап 4. Trello lifecycle

После стабильного Calendar reservation flow подключить создание и обновление одной Trello-карточки на lead, пять согласованных колонок и label `Human Needed`.

После успешного Calendar event система создаёт или обновляет единственную Trello card и перемещает её детерминированным lifecycle-кодом. Только после успешного Trello move lead переходит в `Booked`, а клиент получает финальное подтверждение. При Calendar success и Trello failure событие не создаётся повторно: lead остаётся `Qualified` с pending sync и `Human Needed` при необходимости.

Этап завершён, когда основной и escalation-сценарии корректно синхронизируют Trello, частичный Calendar/Trello failure восстанавливается без дублей, а доска не превращается во внутренний state machine агента.

### Этап 5. Demo Console

После стабилизации Core flow собрать Admin-интерфейс со статусами интеграций, Main Prompt, Pricing Rules, компактным leads/Trello view, ссылкой на Telegram и Miro.

Этап завершён, когда весь MVP1 можно продемонстрировать из одного control center, при этом Trello остаётся операционной CRM.

### Pull Request и Railway Preview

- первый содержательный Pull Request может объединять bootstrap Этапа 1 и законченный vertical slice Этапа 2;
- каждый этап по возможности поставляется отдельным законченным Pull Request;
- каждый новый крупный Pull Request по возможности проверяется в Railway Preview Environment до merge;
- preview-проверка дополняет, но не заменяет локальные tests, lint, typecheck и build;
- перед preview нужно убедиться, что окружение не использует production-данные для опасных или изменяющих сценариев;
- реальные OpenAI-вызовы и внешние side effects в preview выполняются только после отдельного согласования;
- результат проверки preview и все непроверенные ограничения фиксируются перед merge.

## 4. Основные системы

### Telegram

Telegram — основной канал общения с клиентом. Через бота клиент:

- оставляет заявку;
- сообщает параметры уборки естественным языком;
- отвечает на уточняющие вопросы;
- получает рассчитанную стоимость;
- выбирает время;
- получает подтверждение бронирования или сообщение о передаче заявки человеку.

Telegram подключается напрямую через Telegram Bot API. Composio для Telegram не используется.

Для demo-проверок и последующей рабочей эксплуатации используется один и тот же постоянный Telegram-бот. Отдельный demo-бот не создаётся; тестовые диалоги должны использовать явно синтетические данные, а credentials и webhook остаются server-side.

Язык ответа определяется backend детерминированно для каждого incoming customer text: поддерживаются English (`en`), Russian (`ru`), Serbian Latin (`sr-Latn`) и Serbian Cyrillic (`sr-Cyrl`). Явно распознанный язык текущего сообщения имеет приоритет. Для короткого, mixed, numeric-only или неуверенного сообщения backend использует первый уверенно распознанный язык текущей заявки; он сбрасывается только через `New address`. Если такого языка ещё нет, fallback — English. Quote, slots, reservation, escalation и agent prose используют этот locale; callback слота использует ограниченный locale, записанный в самой callback-кнопке. Внутренние данные, Trello, Calendar и Demo Console остаются English.

Клиентский диалог должен звучать как переписка с внимательным координатором Sherlock Cleaning, а не как интерфейс к базе или AI-tool loop:

- отвечать тепло, коротко и естественно, без канцелярита и технических терминов;
- учитывать уже сообщённые сведения, кратко подтверждать понимание и спрашивать только следующий небольшой набор недостающих данных, обычно один-два связанных вопроса за сообщение;
- не выводить названия tools, JSON, UUID, slot tokens, event IDs, названия внутренних статусов (`Qualified`, `Human Needed`) и фразы вроде `team sync`;
- не использовать служебные заголовки, raw field names и длинные анкеты, если разговор можно продолжить обычным вопросом;
- не утверждать, что бот является человеком; если клиент прямо спрашивает, отвечать правдиво от имени цифрового помощника Sherlock Cleaning, сохраняя тот же сервисный тон.

Свободный текст агента считается обычной клиентской прозой и не может передавать произвольный Telegram markup. Backend экранирует его перед отправкой. Форматирование quote, списка слотов, reservation, divider и escalation создаётся типизированным backend-renderer через ограниченный allowlist Telegram HTML. Динамические значения обязательно HTML-escaped. Raw Markdown/MarkdownV2 (`**`, `__`, обратные кавычки и другие управляющие символы) клиенту не показывается.

Список слотов отображается компактно и по правилам Telegram: понятная вводная, локализованные дата/время и до трёх видимых inline-кнопок. Основной выбор выполняется кнопкой; ответ `1`/`2`/`3` и естественные English, Russian, Serbian Latin и Serbian Cyrillic варианты остаются fallback. В видимом тексте и в model-visible tool output нет UUID или slot token. Невидимый callback связывается с конкретным сохранённым token server-side, а Telegram callback обязательно подтверждается, чтобы у клиента не оставался бесконечный spinner.

Перед долгим OpenAI/Calendar шагом бот отправляет best-effort `typing` chat action. Ошибка typing indicator никогда не меняет lifecycle, idempotency или результат основного сообщения.

Во время переписки бот показывает постоянную Telegram reply-keyboard кнопку `New address`. Текст самой кнопки всегда English и не локализуется. Нажатие обрабатывается backend до вызова агента и начинает новую независимую заявку для другого места уборки в том же Telegram chat.

После нажатия бот отправляет фиксированный визуальный разделитель `New cleaning location`. Разделитель и новая граница заказа не генерируются LLM.

Язык определяется для каждого сообщения. Явно распознанный язык сообщения имеет приоритет; для короткого или неоднозначного текста используется первый уверенно распознанный язык текущей заявки, который сбрасывается только через `New address`. Backend до вызова LLM нормализует поддерживаемые даты (`сегодня`, `завтра`, `через N дней`, Serbian/English equivalents, `DD.MM.YY(YY)`) в `Europe/Belgrade`. Запрос `на выходных` предлагает ближайшую субботу и сохраняет дату только после явного подтверждения клиента. Предпочтение morning/midday/evening также является backend-owned и запускает новый ограниченный поиск слотов, а не переименовывает прошлое предложение.

Новая заявка сохраняет только идентичность Telegram chat. `client_data`, address, quote, slot tokens, reservation state, `Human Needed`, OpenAI Conversation, language/script context и summary предыдущей заявки не копируются и не передаются агенту. Предыдущий lead и его Calendar/Trello objects сохраняются как история и автоматически не отменяются, не изменяются и не переводятся в `Lost`. Для нового lead создаётся отдельная OpenAI Conversation, поэтому предыдущая conversation history не участвует в новом заказе.

### Trello

Trello остаётся CRM и операционной системой бизнеса. Demo Console не заменяет Trello и не создаёт параллельный lifecycle.

Trello нужен, чтобы владелец видел бизнес-состояние заявок, мог продолжить нестандартную заявку вручную и сохранил привычный процесс после подключения автоматизации.

### Google Calendar

Google Calendar является источником доступности команд. Для MVP1 используются два отдельных календаря:

```text
Cleaning Team A
Cleaning Team B
```

Подтверждённое бронирование должно быть связано с одной командой и одним событием календаря.

### Composio MCP

Composio используется только как integration layer между агентом и:

- Trello;
- Google Calendar.

Агенту предоставляется минимально необходимый allowlist инструментов.

Для Trello нужны операции создания и чтения карточки, обновления её содержимого, перемещения между согласованными колонками и установки/снятия согласованного label.

Для Google Calendar нужны чтение доступности двух календарей и создание события. Дополнительные действия не подключаются без необходимости.

## 5. Технологический стек

### Приложение

- Next.js App Router;
- TypeScript;
- React;
- Tailwind CSS.

Next.js отвечает за frontend, API routes/server actions, Telegram webhook, бизнес-логику, обращения к OpenAI и интеграции через Composio.

### Hosting

Railway. Для MVP1 предпочтителен один deploy приложения, если фактическая реализация не докажет необходимость отдельного worker или backend.

### Database и Auth

Supabase:

- PostgreSQL;
- Supabase Auth.

### AI

- OpenAI Responses API — выполнение агентного шага;
- OpenAI Conversations API — долговечное состояние диалога.
- OpenAI Agents SDK — runner и typed tool loop одного агента начиная с подэтапа 3A.

Agents SDK является реализационным runtime, а не разрешением переносить бизнес-правила в LLM. Pricing, lifecycle transitions, quote validity, slot calculation, idempotency и разрешение внешних side effects остаются детерминированным backend-кодом.

Связь сущностей:

```text
Telegram chat
→ один активный Lead заказа + исторические Leads
→ отдельная OpenAI Conversation для каждого Lead
```

В собственной базе сохраняется как минимум mapping и явная граница активного заказа:

```text
telegram_chat_id
lead_id
openai_conversation_id
active_in_chat
```

Ограничение `один lead на Telegram chat` заменено на `не более одного активного lead на Telegram chat`. Переключение active lead и создание новой границы заказа должны происходить атомарно.

## 6. Ответственность AI-агента

Один агент отвечает за весь автоматизируемый flow. Он должен:

1. принять сообщение клиента;
2. понять сведения, уже содержащиеся в сообщении и истории;
3. задать только недостающие вопросы;
4. собрать параметры заказа;
5. вызвать backend-функцию расчёта цены;
6. сообщить клиенту quote;
7. проверить доступность двух команд;
8. предложить доступные слоты;
9. получить однозначный выбор клиента;
10. создать событие в календаре выбранной команды;
11. сохранить бронирование и идентификаторы интеграций;
12. поддерживать актуальное бизнес-состояние карточки Trello;
13. распознать нестандартный или неуверенно классифицированный запрос;
14. поставить `Human Needed` и передать человеку все собранные данные без потери контекста.

LLM отвечает за понимание естественного языка, диалог, извлечение параметров, определение недостающей информации, формирование ответа и выявление нестандартного запроса.

LLM может выбрать следующий разрешённый semantic tool: запросить недостающие данные, рассчитать quote через backend, запросить availability, предложить сохранённые slot tokens или эскалировать заявку. LLM не получает произвольных низкоуровневых инструментов для изменения lifecycle или внешних объектов.

LLM не рассчитывает деньги, не придумывает доступность команды, не выбирает несуществующий slot, не определяет допустимость lifecycle transition и не подтверждает финальное бронирование до успешных Calendar и Trello side effects.

## 7. Данные заявки

Минимальный набор данных:

```text
cleaning_type
area_m2
rooms
bathrooms
heavy_pet_hair
extras
address_or_district
preferred_date
urgency
```

После расчёта и бронирования добавляются:

```text
quoted_price_rsd
assigned_team
booked_start
booked_end
trello_card_id
calendar_event_id
human_needed
human_needed_reason
```

Агент не повторяет вопрос, если клиент уже дал пригодный ответ. Данные можно собирать за несколько сообщений; диалог должен оставаться естественным.

Данные предыдущих заявок того же Telegram chat не считаются уже сообщёнными данными новой заявки. Нажатие `New address` является backend-owned reset boundary: агент не решает сам, переносить ли старые поля или conversation history.

## 8. Детерминированный pricing

Цена вычисляется обычной типизированной backend-функцией из сохранённых входных параметров. Prompt может выбрать или уточнить параметры, но не выполняет арифметику и не переопределяет правила.

### Типы разовой уборки

#### Standard cleaning

```text
80 RSD / m²
minimum 4 000 RSD
```

#### Deep cleaning

```text
160 RSD / m²
minimum 9 000 RSD
```

`Standard cleaning` означает один разовый стандартный заказ. Повторяющиеся уборки и расписания не поддерживаются.

Базовая формула:

```text
base_price = max(area_m2 × rate, minimum_price)
```

### Комнаты и санузлы

Количество комнат сохраняется и передаётся команде, но напрямую не влияет на цену.

Первый санузел входит в базовую стоимость. Каждый дополнительный санузел добавляет `500 RSD`.

### Домашние животные

Само наличие питомца не увеличивает цену. Только `heavy_pet_hair = true` добавляет `900 RSD`.

### Дополнительные услуги

| Extra | Доплата |
|---|---:|
| `windows` | 900 RSD |
| `oven_inside` | 1 000 RSD |
| `fridge_inside` | 900 RSD |
| `balcony_or_terrace` | 1 000 RSD |

### Скидка за площадь

Скидка применяется к базовой стоимости:

| Площадь | Скидка |
|---|---:|
| до 100 m² включительно | 0% |
| 101–150 m² | 5% |
| 151–200 m² | 10% |

### Срочный заказ в тот же день

Для same-day заказа применяется наценка `20%` после расчёта базовой стоимости, скидки и доплат.

### Порядок расчёта

```text
1. base = max(area_m2 × rate, minimum_price)
2. discounted_base = base × (1 - volume_discount)
3. subtotal = discounted_base + bathroom_surcharge + pet_hair_surcharge + extras
4. total = subtotal × 1.20, если заказ same-day; иначе subtotal
5. округлить итог до ближайших 100 RSD; при положительной ровной середине округлить вверх
```

Правило округления фиксировано для MVP1 и должно быть покрыто тестами.

## 9. Когда автоматическая цена запрещена

Агент не выдаёт автоматическую цену и устанавливает `Human Needed`, если:

- площадь больше 200 m²;
- нужна уборка после ремонта;
- объект коммерческий;
- заявлено необычно сильное загрязнение;
- нужны услуги вне стандартного списка;
- запрос нельзя уверенно классифицировать;
- агент не уверен, что правильно понял scope;
- обязательных данных недостаточно, а получить уточнение не удаётся.

Уже собранные данные и причина эскалации сохраняются в базе и Trello.

## 10. Scheduling двух команд

После принятия quote агент проверяет доступность `Cleaning Team A` и `Cleaning Team B` на желаемую дату и предлагает только реально свободные слоты, представленные сохранёнными server-side slot tokens.

Календарное событие создаётся только после явного выбора клиента и повторной проверки доступности. Calendar reservation считается успешной, только если:

- слот повторно подтверждён как доступный;
- событие создано в календаре конкретной команды;
- `calendar_event_id`, команда и интервал сохранены в базе;

Финальное бронирование считается успешным, только если дополнительно:

- карточка Trello переведена в `Booked`;
- клиент получил подтверждение.

Если создание события завершилось ошибкой, агент не сообщает о резервации или успешном бронировании. Если Calendar event создан, но Trello move не подтверждён, событие не создаётся повторно, lead остаётся `Qualified` с pending sync, а финальное confirmation не отправляется.

Scheduling использует `Europe/Belgrade`, Mon–Sat 08:00–20:00, Sunday closed. Standard занимает `area / 25 m²` часов, Deep — `area / 15 m²`; длительность округляется вверх до 30 минут, минимум 2 часа, после уборки резервируется 30-minute buffer. Агент ищет до трёх слотов на 30-minute grid от preferred date максимум на 14 дней вперёд; для same-day не предлагает время раньше чем через два часа.

Каждая выдача слотов имеет стабильный server-side порядок `1..3`. Новая выдача атомарно делает предыдущие невыбранные варианты неактивными; повторный availability request не может привести к выбору слота из старого списка. При одинаковом времени порядок команд детерминирован. Inline callback может содержать opaque server-side reference, но reference не отображается клиенту и не передаётся в model-visible tool result.

## 11. Trello lifecycle

Trello показывает только бизнес-состояние заявки, а не внутренний state machine агента.

Используются ровно пять колонок:

```text
New Lead
Qualified
Booked
Done
Lost
```

### New Lead

Карточка создаётся при появлении нового клиента. Здесь остаются заявки, по которым идёт первичный разговор, собираются данные и ещё нет готового quote.

### Qualified

Lead становится `Qualified`, когда основные параметры и scope понятны, цена рассчитана и клиент получил quote. Это реальный потенциальный заказ с понятными условиями и стоимостью.

### Booked

Lead становится `Booked`, когда клиент согласился, выбрал слот, событие успешно создано в Google Calendar и существующая Trello-карточка подтверждённо перемещена в `Booked`. Только после обоих side effects клиент получает финальное confirmation. Это финальная точка автоматизируемого Core flow.

### Done

Уборка выполнена. В MVP1 карточка переводится в `Done` вручную.

### Lost

Заявка не превратилась в заказ: клиент явно отказался либо владелец вручную закрыл её как потерянную. Сложное автоматическое определение `Lost` не требуется.

### Human Needed

`Human Needed` не является колонкой и не заменяет lifecycle status. Это label/flag, который может стоять на карточке в любой колонке, например:

```text
New Lead + Human Needed
Qualified + Human Needed
```

Label должен сопровождаться краткой конкретной причиной ручного участия.

## 12. Минимальное содержание Trello-карточки

Trello не дублирует базу целиком. Карточка показывает только данные, необходимые человеку для продолжения работы.

Рекомендуемый title:

```text
Client name · District · Area m²
```

Минимальное описание после появления соответствующих данных:

```text
Contact
Cleaning type
Area / rooms / bathrooms
Extras and heavy pet hair
Address or district
Preferred date
Quoted price
Assigned team and booked time
Short conversation summary
Human attention reason, if applicable
```

Карточка создаётся один раз на lead и обновляется при значимых изменениях, а не после каждого сообщения.

Frontend — единое окно демонстрации и настройки автоматизации, но не новая CRM.

Demo Console должен содержать:

- статусы Telegram, Trello, Team A Calendar и Team B Calendar;

## 14. Конфигурация агента

Main Prompt и Pricing Rules хранятся в БД. Admin может увидеть, изменить и сохранить их.

Новый агентный шаг должен использовать актуальную сохранённую версию. Для воспроизводимости lead или conversation должен быть связан с использованной версией конфигурации либо конфигурационный snapshot должен сохраняться в activity log.

Изменение prompt не может обойти детерминированную pricing-функцию, правила эскалации или ограничения инструментов.

## 16. Надёжность и идемпотентность

- повторная доставка Telegram webhook не должна создавать второй lead или вторую карточку;
- один Telegram chat может иметь несколько исторических leads, но не более одного активного; `New address` атомарно переключает активную заявку и не переносит order context;
- повторная доставка одного reset update и повторное нажатие до появления данных новой заявки не создают цепочку пустых leads или Conversations;
- `processed` Telegram update не обрабатывается повторно, а `failed` или безопасно признанный stale update можно атомарно повторно захватить;
- разные updates одного Telegram chat сериализуются до чтения и изменения lead и OpenAI Conversation;
- повторный агентный шаг не должен создавать дубликат календарного события;
- одна заявка связана максимум с одной активной Trello-карточкой;
- переход в `Booked` выполняется только после успешных Calendar write и Trello move;
- внешние идентификаторы сохраняются сразу после успешного действия;
- ошибки интеграций журналируются без секретов;
- при частичном сбое система сохраняет прогресс и показывает, что требует повторения или ручного участия;
- `Human Needed` не меняет lifecycle status, а неактуальность quote хранится отдельно от lifecycle;
- входящие webhooks должны проверяться доступным способом, а административные routes — требовать session;
- timezone и даты должны храниться и передаваться однозначно.

## 17. Безопасность и стоимость

- Telegram token, OpenAI API key, Supabase service credentials и Composio credentials хранятся только в server-side environment variables;
- секреты не попадают во frontend, логи, Git, Trello или Miro;
- внутренние UUID, slot tokens, tool payloads и external IDs не попадают в клиентский Telegram-текст;
- agent tools ограничиваются allowlist и минимальными правами;
- административные изменения prompt и pricing должны быть доступны только Admin;
- реальные платные OpenAI-прогоны требуют отдельного согласования с моделью, объёмом, числом прогонов и верхней оценкой стоимости;
- локальные тесты по умолчанию используют fake/stub adapters и не обращаются к платным API;
- production deploy, cloud provisioning и изменение production-данных выполняются только после отдельного подтверждения.

## 18. Основной demo-сценарий

1. Клиент пишет боту о разовой уборке квартиры и сразу сообщает часть параметров.
2. Создаётся один lead и одна карточка `New Lead`.
3. Агент извлекает уже известные параметры и задаёт только недостающие вопросы.
4. Backend-функция рассчитывает цену; клиент получает quote.
5. Карточка переходит в `Qualified`.
6. После согласия клиента агент проверяет два календаря и предлагает свободные слоты.
7. Клиент выбирает один слот.
8. Система создаёт событие в календаре конкретной команды и сохраняет внешний ID.
9. Карточка переходит в `Booked`.
10. Клиент получает подтверждение с датой, временем, командой и стоимостью.
11. Demo Console отражает актуальные интеграции, lead и activity.

Для демонстрации повторного обращения клиент нажимает `New address`, получает fixed divider, отправляет данные другого объекта и проходит новый независимый flow; язык первого нового сообщения определяется независимо от предыдущего заказа. Предыдущая заявка остаётся в истории, но её адрес, параметры, quote, slots, OpenAI Conversation и language/script context не влияют на новую.

Отдельный demo-сценарий проверяет нестандартный запрос: цена не выдается, данные сохраняются, карточка остаётся в своём lifecycle status и получает `Human Needed` с причиной.

## 19. Критерии приёмки MVP1

MVP1 считается готовым, когда подтверждено, что:

- Telegram webhook принимает сообщения и не дублирует обработку;
- conversation продолжает диалог с сохранённым контекстом;
- язык ответа и Serbian script переключаются по каждому meaningful customer text; ambiguous/numeric-only input получает durable primary locale текущей заявки или English до первого уверенного текста, а quote, slots, callback и reservation сохраняют locale текущего turn;
- постоянная кнопка `New address` создаёт отдельную активную заявку в том же chat, показывает fixed divider и исключает order/language context предыдущего заказа из нового agent turn;
- сообщения звучат как естественный сервисный диалог, не содержат raw Markdown, технических статусов, tool names, UUID или видимых slot tokens;
- quote, slots, reservation и escalation корректно рендерятся Telegram HTML-renderer, а динамические значения экранируются;
- слоты выбираются видимыми inline-кнопками с numbered fallback; повторный список не позволяет выбрать старый вариант, callback подтверждается без зависшего spinner;
- duplicate reset update и двойное нажатие до нового пользовательского сообщения не создают лишние leads или OpenAI Conversations;
- агент не переспрашивает уже известные обязательные данные;
- одинаковые pricing inputs всегда дают одинаковый результат;
- pricing unit tests покрывают minimum, скидки, extras, дополнительные санузлы, pet hair, same-day и границы 100/101/150/151/200 m²;
- запросы вне автоматического scope не получают выдуманную цену;
- Calendar availability читается для обеих команд;
- подтверждение создаёт ровно одно событие и сохраняет его ID;
- Trello использует только пять согласованных колонок;
- `Human Needed` реализован label/flag, а не шестой колонкой;
- `Done` и сложные случаи `Lost` не автоматизированы сверх scope;
- Demo Console позволяет Admin изменить prompt и pricing rules;
- Miro и Telegram доступны из Demo Console;
- ни один секрет не виден во frontend или репозитории;
- основной и escalation demo-сценарии проверены end-to-end в безопасной среде;
- Gmail, recurring cleaning и `Next Week` отсутствуют в продукте и навигации.
